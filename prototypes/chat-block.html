    Why the original stays on the canvas

    You asked for this explicitly, and it is the decision the whole model hangs off. If dragging a block into a conversation moved it, the chat would become a place work goes to get lost — and the person who shared it would be the one who lost it. So a drag creates a reference: one block, two views.

    That is why blocks exists as a table at all. A block is a row with an id, so a chat message can point at it. Before migration 0007 a notebook was one JSON blob and there was nothing smaller than the whole project to point at.

    The three levels, and which one this is

    • Block — what the drag above creates. One block, nothing around it.
    • Sheet — from the sidebar. That sheet's blocks, and no other sheet in the project.
    • Project — everything, including sheets you add later.

    Use the dropdown on a reference card to widen or narrow a live share and watch what appears on Mara's side. Widening from block to sheet is one UPDATE; it does not create a second grant.

    What revoking actually does

    Press Revoke on a card. The block disappears from Mara's canvas — but so does the stored copy. blocks.data is populated only while a live share reaches the block, and set back to NULL the moment it does not. A revoke that leaves the bytes behind is a revoke in the interface only.

    That is also why sharing does not double anybody's storage. A workspace with no shares stores exactly what it stored before the feature existed.

    The one thing that is faked here

    Attribution flags appear instantly in this prototype. In the real app the stamp comes from a trigger reading auth.uid(), so it arrives on the next pull rather than on the next keystroke — and it cannot be forged by a client, which is the entire reason it is worth drawing.

    Everything else — which blocks appear, what a revoke removes, what widening a grant changes — matches what the schema does today.
